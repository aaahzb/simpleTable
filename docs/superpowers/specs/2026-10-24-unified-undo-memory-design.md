# 统一内存预算撤销/重做与全文档操作设计

- 日期：2026-10-24
- 基线：`e5f5998`
- 状态：设计已分节确认，等待书面审阅；尚未实施
- 实施分支：`feat/unified-undo-memory`

## 1. 背景与目标

阶段 25 已把单元格批量操作改成一次用户操作一条历史，但仍存在以下限制：

- 撤销历史同时受固定条数和单条字符预算限制，不能按实际历史体量自然决定步数。
- 列执行会物理重写整档并重建会话，无法撤销。
- 排序、首行/无表头切换会清空历史。
- 大复制、大粘贴和整行/整列清除仍可能先构造完整文本、二维数组或任务数组，再进入引擎预算检查。
- 保存会物化行结构并重开文件，旧历史是否仍能安全寻址必须由明确转换保证，不能只依赖“记录号稳定”的假设。

本设计的目标是：

1. 每个文档使用固定、可配置的撤销/重做历史预算，常规小操作保留多步，大操作自动减少可保留步数。
2. 所有文档操作都进入同一历史体系，包括内容、粘贴、插删行列、清除、排序和首行/无表头切换。
3. 单步历史需求超过预算时，在执行前确认；成功后建立固定点，之后的新操作可以撤销，但不能越过固定点。
4. 历史与执行路径都按超省内存设计，不复制整表，不因获得固定点机制就放松每步存储要求。
5. 大复制粘贴使用有界分块和本机磁盘中转，取消或失败时不留下半次修改。

## 2. 已确认的产品决策

| 项目 | 决策 |
|---|---|
| 默认历史预算 | 每个打开文档 64 MiB，即 67,108,864 字节 |
| 预算作用域 | 每个页签独立；设置为全局默认值，可下发到所有已打开文档 |
| 撤销与重做 | 共用同一预算，不分别配置 |
| 步数 | 取消固定 200 条的主限制，由历史体量和结构开销决定 |
| 动态预算 | 不采用；系统可用内存只用于执行前安全提示 |
| 文档操作范围 | 内容、粘贴、插删行列、清除、排序、首行/无表头切换 |
| 纯界面状态 | 筛选、选区、光标、滚动位置不进入撤销历史 |
| 固定点 | 此前历史与本次操作不可撤销；之后的新操作可撤销到固定点 |
| 普通保存 | 通过身份转换尽量保留历史，失败不得静默损坏 |
| 排序保存 | 若存在历史，确认物化并建立固定点后才能保存 |
| 列执行 | 会话内映射生效并标脏，原 CSV 延迟到保存时才重写 |
| 大型复制 | 超过 8 MiB 使用应用内流式剪贴板，不写系统剪贴板 |
| 远程操作 | 不执行远程推送或其他远程写操作 |

## 3. 调研依据与预算策略

### 3.1 成熟软件的做法

- [Blender：System Preferences / Memory & Limits](https://docs.blender.org/manual/en/latest/editors/preferences/system.html#memory-limits) 提供固定的 Undo Steps 和 Undo Memory Limit，内存单位为 MiB 语义下的 MB 设置，0 表示不限制。
- [GIMP：System Resources](https://docs.gimp.org/3.0/en/gimp-prefs-system-resources.html) 提供 Maximum undo memory 和 Minimal number of undo levels；超过固定内存时删除最旧历史，但保留配置的最少步数。
- [Emacs：Maintaining Undo](https://www.gnu.org/software/emacs/manual/html_node/elisp/Maintaining-Undo.html) 使用固定字节阈值，历史大小包括保存文本和其他数据；`undo-outer-limit` 是防止内存溢出的最后防线，当前命令超限时会丢弃撤销信息并警告。
- [Microsoft：MEMORYSTATUSEX](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex) 将 `ullAvailPhys` 定义为当前可立即复用的物理内存，包含待机、空闲和零页列表；它反映瞬时系统状态，不是稳定的应用历史容量。

### 3.2 本项目选择

采用“固定历史预算 + 最旧历史淘汰 + 单步超限固定点”。理由：

- 固定预算使用户在不同时间、不同系统负载下获得一致的历史语义。
- 不把可用物理内存按比例分配为历史，避免其他程序、页缓存和多页签导致历史容量忽大忽小。
- 现有排序内存估算继续使用系统可用内存做执行风险提示，但不改变历史预算。
- 不采用 GIMP 的最少步数保底；本项目对单步超限已有明确的固定点确认语义。
- 不把每一步都保存为完整文件代际。文件代际只作为超大操作的有界执行方式，不作为普通历史的默认存储。

## 4. 术语与边界

- **历史体量**：历史记录自有元数据、逻辑快照内容和共享保留对象的统一记账值。它是确定性的预算账目，不等同于进程 RSS。
- **固定点**：一个不能由撤销越过的文档状态。固定点由成功执行的超大操作或明确确认的物化操作建立。
- **物化**：把逻辑行序、列映射或编辑层写成新的物理布局。
- **会话临时文件**：只供当前应用进程或当前文档会话使用的本机临时数据，不作为用户文档，不上传到外部服务。
- **执行内存**：解析、排序键、分块缓冲和提交期间的临时内存，与历史预算分开管理。

本设计不承诺：

- 应用重启后恢复撤销历史。
- 大型复制与外部程序之间继续保持系统剪贴板互通。
- 通过磁盘中转无限保留历史。
- 把 64 MiB 解释为整个进程的内存上限。
- 在异常崩溃后跨实例自动清理所有临时文件；正常关签、退出和对象释放必须清理。

## 5. 统一历史核心

### 5.1 历史记录与容器

撤销和重做统一由 `HistoryLedger` 管理，内部使用支持高效头部淘汰的双端容器。每个历史项至少包含：

- 具体操作及其稳定身份数据。
- 自有元数据字节数。
- 对共享历史分配对象的引用。
- 内容脏点效果：内容操作或仅视图操作。
- 必要的校验信息和物化转换信息。

`UNDO_CAP = 200` 不再作为主限制。不得另设一个较低的固定条数来绕过字节记账；大量小操作的条目、指针和对齐开销本身就会消耗预算。

### 5.2 记账规则

历史预算采用确定性、可测试的估算规则：

1. 字符串按保留内容的 UTF-8 字节及实际容器容量记账。
2. `Vec`、`HashMap`、枚举、对齐、行块、列映射和排序排列都计入结构开销。
3. 所有累加使用 checked arithmetic；溢出按单步超限处理，但必须在写入前返回明确错误。
4. 同一共享分配只计一次。历史项持有共享分配标识，最后一个历史引用释放时才从账本扣除；仅活动文档持有的部分不算历史。
5. 撤销与重做之间移动历史项时不深拷贝，历史总账不因单纯移动而改变。
6. 原始 mmap 中的旧值优先使用引用，不复制字符串。为保证保存前后账目稳定，引用按其指向的逻辑内容长度计入历史预算，但整个 mmap 文件不计入。
7. 磁盘冷快照仍按其逻辑内容计入历史预算，不能用临时文件绕过单步固定点判断。
8. 分配器、操作系统页缓存和进程 RSS 不作为逐条历史的计量单位；预算约束的是引擎可确定核算的历史体量。

### 5.3 入栈、淘汰与空操作

新文档操作遵循以下顺序：

1. 完整预检地址、结构限制和实际变化；空改动直接返回，不请求固定点确认。
2. 计算精确历史成本和执行方式。新项成本大于预算时，先转固定点确认，不得先写入再补确认。
3. 普通操作在确认无需固定点后执行；任何失败都不得清空 redo 或淘汰旧历史。
4. 成功后清除 redo，并把新项加入 undo。
5. 新项成本等于预算时只保留该项；小于预算时保留尽可能多的新旧历史。
6. 总账超预算时，从最旧 undo 项开始淘汰，直到不超预算。
7. undo/redo 只移动既有记录，不额外深拷贝，因此不因移动而触发新的历史膨胀。
8. 空改动、空撤销和空重做不增加 revision、不改预算、不标脏。

预算调大不会恢复已淘汰内容。预算调小时，先从最旧 undo 端淘汰；若仍有 redo 且需要继续降账，则从 redo 时间线最远端开始淘汰，以保留距离当前状态最近且依赖链完整的重做序列。不得从 redo 中间抽项。若按此顺序只剩一条记录且它仍超过新预算，则清空双栈并把当前状态记为固定点；设置确认框必须事先说明这一结果。所有已打开文档接收新预算，但各文档独立记账和淘汰。

### 5.4 固定点状态机

固定点必须经过以下状态转换：

1. **预检**：确定操作范围、估算或精确历史成本、执行临时空间和失败回滚方式。
2. **确认**：只有单步历史成本超过预算，或物化无法安全保留历史时，才显示固定点确认。
3. **暂存执行**：在有界内存中完成临时文件、临时块或新会话代际；此时尚不修改活动文档。
4. **原子提交**：校验成功后一次切换活动状态，再清空双栈并记录固定点。
5. **后续操作**：正常进入历史；撤销到固定点时 `canUndo = false`，不继续进入固定点前状态。
6. **取消或失败**：活动数据、历史、脏点和 redo 保持原状，临时产物按所有权清理。

固定点确认文案必须明确：此前历史与本次操作不可撤销，之后的新操作可以撤销到固定点。

## 6. 稳定身份与文档操作

### 6.1 稳定列身份与列撤销

引入会话内稳定的 `ColumnId`，物理列下标只表示存储位置，不再作为长期历史身份。

核心状态：

- 当前逻辑列顺序为 `Schema` 中的 `ColumnId` 映射。
- 原始列、插入列和已删除但仍被历史引用的列具有不同存储来源。
- `CellId` 的列部分改为稳定 `ColumnId`。
- 筛选、排序和粘贴开始时解析稳定列身份，避免列撤销后写到其他列。
- `Schema` 使用共享不可变对象；未改变的 schema 不因历史记录而复制。

列 pending 预览继续保留。一次“执行列操作”把当前 pending 序列合并为一条 `Op::Columns`，保存执行前后的 schema 与必要列名状态：

- 插入列只增加映射和空值稀疏存储。
- 删除列只移除可见映射，底层数据在历史仍需要时保留。
- 重命名只保存列名变化。
- 撤销/重做只切换逻辑映射，不重写整档。
- 历史淘汰后，不再被活动文档或其他历史引用的插入列数据可以回收。

执行列操作不再直接改写原 CSV。操作成功后文档标脏，保存时才按当前 schema 流式投影写出。

### 6.2 单元格与范围操作

现有 `SetCell`、`SetCells` 和 `Paste` 保留一次用户操作一条记录的语义，并接入统一账本。

为减少额外副本：

- 原始未编辑值优先保存源引用。
- 活动覆盖层与历史之间共享必须共同保留的值对象。
- 插入块在活动文档与历史之间移动或共享所有权，不分别深拷贝整行。
- 空字符串和重复结构使用共享表示，不为每格制造独立分配。

整行、整列和矩形清除使用结构化范围命令。前端只传行号、列号或范围，不再构造“行数 × 列数”的任务数组。引擎在迭代过程中生成稀疏旧值记录并按统一预算处理。

### 6.3 粘贴与自动扩列

粘贴扩列和内容写入必须合并为一个用户级 `Op::Paste`：

- schema 变化与既有格变化、末尾新增行共同校验。
- 撤销同时恢复列结构和粘贴前内容。
- 重做同时恢复扩列和粘贴结果。
- 不再先执行一个会清历史的列操作，再发现粘贴预算失败。
- 取消、地址非法、预算处理失败或粘贴失败时，列数、内容、历史和 redo 均不变。

不引入任意操作组成的通用 Composite；只扩展具有明确不变量的专用操作。

### 6.4 排序

排序历史保存共享的不可变行号排列，不保存整行内容或排序键。

- `Op::Sort` 保存排序前后的排列对象及排序规则。
- 未排序状态使用恒等视图，不分配完整恒等排列。
- 活动文档与历史共享排列。
- 反向 rank 在撤销、重做或筛选映射需要时临时建立，完成后释放，不在每个历史项中长期保存双份排列。
- 撤销和重做恢复精确排列，不重新执行排序键计算。
- 退出排序表示为从当前排列回到恒等视图的排序操作，因此也可撤销/重做。
- 排序期已有的结构编辑限制可以继续保持；本期目标是把排序本身纳入历史，不是放开所有排序态编辑。
- 筛选命中集在排序撤销/重做后按稳定行身份恢复或重算，不能沿用错误显示位置。

排序属于视图操作，进入、退出、撤销和重做本身不额外增加内容 revision。排序保存是物化操作，按第 7.3 节处理。

### 6.5 首行/无表头切换

首行模式使用专用 `Op::HeaderMode`，记录：

- 切换前后的 headerless 状态。
- 原表头、目标表头和列数。
- 顶部行被提升或恢复为数据行所需的身份与内容引用。
- 渐进索引已完成和未完成两种路径所需的明确状态。

实现不得批量平移所有源记录编号。表头与顶部行的转换必须通过稳定行身份和可逆操作完成。

切换后筛选和收窄基准按现有规则失效。该操作进入历史，但保持当前“视图属性本身不额外标脏”的规则。若顶部行自身历史成本超过预算，同样走固定点确认。

## 7. 行快照、保存与身份转换

### 7.1 删除行历史必须自包含

删除源行不能只保存旧记录号并假定原字节永远可用。历史必须保留恢复所需内容或受生命周期管理的源引用：

- 小行使用内存中的紧凑行快照。
- 大行或批量删除使用会话临时存储及稀疏索引。
- 保存导致源引用失效前，历史仍需要的部分必须已完成迁移。
- 删除内容也计入统一历史预算；超过单步预算时走固定点。

当旧源记录已经物化消失时，撤销删除可以恢复为插入行。恢复后必须重绑定更早历史中指向该行的单元格身份，不能制造重复行或写入其他记录。

### 7.2 普通保存的 BaselineTransform

普通保存先生成 `BaselineTransform`，再执行物化。转换描述：

- 连续幸存源行的旧记录区间到新记录区间，内存量为段数而非行数。
- 插入行到物化后记录的稀疏映射。
- 被删除源记录及其历史快照的新恢复方式。
- 当前列 schema 到保存后物理列的映射。
- 所有 undo/redo 中单元格、行操作和块引用的处理规则。

删除列是普通保存的重要例外：若当前 schema 已不包含某列，而 undo/redo 仍需恢复该列，物理保存后来源会消失。本设计不为此复制整列或保留整表旧档；这种保存归入物化保存，存在上述历史时必须先确认固定点。若相关历史已淘汰，或该列仍在当前 schema 中、保存后底层数据仍存在，则可继续普通转换。

保存前必须证明所有保留历史都能转换。转换所需内存先预留，源引用先迁移，然后再写临时文件和替换目标。成功重开后，身份重绑定应是无失败、无额外大分配的提交步骤。

无法完整证明转换安全时，不得继续“保存但保留无效历史”。必须先说明原因，并由用户选择固定点保存或取消保存。

### 7.3 排序保存

排序保存会把任意显示排列物化为新的物理行序。为控制首版复杂度和磁盘开销：

- undo 和 redo 都为空时维持直接保存。
- undo 或 redo 任一有记录时，保存前明确提示将建立固定点。
- 取消则文件和会话不变。
- 确认并成功保存后，物理顺序成为新固定点，双栈为空，revision 归零。
- 之后的新操作可以正常撤销到该固定点。

### 7.4 保存失败与回归保护

保存临时文件、替换、重开和历史转换必须视为一个提交过程。任何可恢复失败都不得留下“文件已变、历史却按旧身份解释”的状态。可重开校验和历史转换准备必须在临时文件阶段完成；目标替换是唯一提交点，替换后不得再执行可能失败的身份转换。

以下场景必须先写回归测试，再修改保存实现：

- 插入行 → 保存 → 撤销插入。
- 删除行 → 保存 → 撤销删除并核对全部原始位置。
- 插入块之后的源格编辑 → 保存 → 撤销，确认不写错行。
- 删除行与更早单元格历史交错 → 保存 → 连续撤销。
- 列结构、行结构与单元格操作交错 → 保存 → 完整往返。
- 删除列后仍存在恢复该列的历史 → 保存，分别验证取消与固定点确认。
- 排序保存取消与确认两条路径。

## 8. 有界复制、粘贴与临时存储

### 8.1 复制

小复制维持现有 TSV 和系统剪贴板行为。流式大复制首版只支持完整矩形；非矩形多选区维持现有行为，不得为绕过体量限制而在前端拼接完整文本。应用内剪贴板只在同一应用进程内共享，不承诺跨独立进程。

完整矩形复制结果超过 8 MiB 时：

1. 引擎流式序列化到应用内临时剪贴板文件。
2. 前端只接收令牌、行列数、UTF-8 字节数和格式版本，不接收完整文本。
3. 不调用系统剪贴板写入。
4. 状态栏明确提示“已复制大区域，仅可在本应用内粘贴”。
5. 新的复制替换旧的应用内大剪贴板；关闭来源页签不得破坏其他页签仍可使用的应用内剪贴板。

应用内大剪贴板由进程级所有者管理，随替换和应用退出清理；它不属于来源文档会话。应用重启后不保留。

剪切必须先等待复制成功，再执行清除。复制失败时不得清除选区；清除本身仍是一条可撤销内容操作。

### 8.2 外部粘贴

`navigator.clipboard.readText()` 对超大外部文本仍会先产生一份完整 JavaScript 字符串，这是当前 Web API 的固有限制。本设计不宣称消除这一份分配。

读取后：

- 小文本维持现有解析路径。
- 大文本按不超过 1 MiB 的块写入临时文件，分块累计 UTF-8 大小，不为计量再编码全文。
- 不在 JavaScript 中构造完整二维 `rows`，不通过一次 IPC 发送完整粘贴块。
- 引擎流式解析，先得到维度、目标合法性、精确历史成本和执行方式，再提交。
- 取消固定点或任何分块失败时，活动文档不变。

### 8.3 内部粘贴与固定点物化

内部大粘贴直接读取应用内临时剪贴板，不经过 JavaScript 全文。

普通可撤销粘贴生成有界的稀疏历史和插入块。单步超过预算时：

1. 在执行前请求固定点确认。
2. 使用会话临时文件流式合并当前文档与粘贴输入。
3. 校验行数、列数、编码和提交范围。
4. 成功后切换会话代际并建立固定点。
5. 用户的原 CSV 不因此提前修改，只有显式保存才写回用户路径。

### 8.4 临时文件所有权与清理

- 文档会话临时文件由对应文档所有，关签、正常退出和对象释放时清理。
- 应用内大剪贴板独立所有，随替换和退出清理。
- 保存临时文件仍位于目标同目录，以保证同卷原子替换。
- 会话 spool 不用于最终原子换名，避免跨卷假设。
- 创建前检查临时卷空间和路径权限；空间不足时拒绝执行，活动文档不变。
- 多实例下不得删除其他活动实例的目录。本期不做崩溃后跨实例自动清扫，异常遗留交由系统临时目录机制处理。
- 临时数据只留在本机用户临时区域，不发送到外部服务。

## 9. 设置、提示与脏点

### 9.1 设置持久化

复用现有注入式 localStorage 偏好模式，新增独立设置键，不引入新的 Tauri store 依赖。

工具栏在“快捷键”前新增“撤销内存…”按钮，打开数值对话框。确认时校验并应用，取消不改任何文档。对话框说明预算按文档独立计算、撤销和重做共用，以及降低预算可能淘汰历史或形成固定点。

- 默认值：64 MiB。
- 可配置范围：1 MiB 至 1,024 MiB。
- 存储单位：MiB 整数值；引擎接收 checked 后的字节数。
- 非法、损坏或越界设置回退到 64 MiB。
- 启动时下发每个新会话；修改时下发所有打开会话。
- 每文档独立使用预算，页签关闭立即释放对应历史。

### 9.2 固定点提示

超大操作提示包含：操作类型、所需历史体量、当前预算，以及“此前历史与本次操作不可撤销，之后可撤销到固定点”的结果。

排序保存使用专门的物化提示，不复用模糊的“列历史清空”文案。

大型复制提示只说明应用内可用，不能暗示外部程序已经收到剪贴板文本。

### 9.3 脏点与通知

- 内容、粘贴、插删行列按内容操作维护 revision。
- 列执行现在只改变会话逻辑状态，因此成功后必须标脏。
- 排序和首行模式进入历史，但不因视图状态本身额外增加内容 revision。
- 普通保存成功后 revision 归零，保留已经安全转换的历史。
- 排序固定点保存成功后 revision 归零，双栈为空。
- 空操作、取消和失败不发数据修改通知，不改变撤销按钮状态。
- `canUndo`/`canRedo` 必须反映固定点和实际栈状态，不能出现按钮可用但引擎假成功。

## 10. 错误处理与原子性

以下情况都必须在活动文档写入前处理：

- 地址、列号、行号、排序或索引状态非法。
- 历史成本计算溢出或超过预算。
- 粘贴分块中断、剪贴板令牌失效或格式不支持。
- 临时目录不可写、磁盘空间不足、编码或结构校验失败。
- 保存身份转换不完整。
- 固定点或排序保存确认被取消。

执行失败时保留原数据、原历史和 redo。已经写入的临时文件可以按恢复策略保留，但不得被活动会话部分采用。

正常提交后才清理被替代的历史和临时对象。不得为了提前释放内存而在提交前清空 undo/redo。

## 11. 分阶段实施

本设计按依赖拆成以下垂直阶段，每个阶段都遵循先 RED 后 GREEN，不一次性重写整个引擎。

### P0：特征化与现有边界

- 为保存后的插入、删除、单元格身份补充回归测试，先记录真实行为。
- 固定现有复制、粘贴、列执行、排序和表头模式的语义基线。
- 记录内存与操作耗时的测试夹具和测量方法。

### P1：HistoryLedger 与固定点基础

- 统一成本模型、双端历史容器、64 MiB 设置和最旧淘汰。
- 所有现有历史变体接入账本。
- 固定点确认、成功提交、失败保持和后续撤销边界。
- 接入范围命令，先消除整行/整列清除的前端任务数组。

### P2：稳定列与列结构撤销

- 引入 `ColumnId` 和共享 `Schema`。
- 读、写、筛选、排序和粘贴使用稳定列身份。
- pending 执行改列映射历史，列执行标脏，保存按映射投影。
- 粘贴扩列合并到专用 Paste 历史。

### P3：行快照与普通保存转换

- 删除行历史自包含，补充必要的会话临时存储。
- 实现 `BaselineTransform` 和普通保存历史重绑定。
- 修复保存后插删行和单元格撤销的身份风险。

### P4：排序与首行模式历史

- 共享排序排列、临时 rank、筛选映射和退出排序历史。
- 首行/无表头专用可逆操作。
- 排序保存固定点确认。

### P5：流式剪贴板与超大固定点执行

- 应用内大复制、外部粘贴分块、内部直接粘贴。
- 大粘贴精确预检和会话代际提交。
- 临时空间、取消、失败和清理链。

### P6：优化、真机验证与发布

- 检查所有共享对象和临时分配，去除不必要克隆。
- 完整 Node、Rust、debug/release 真机冒烟。
- 大文件内存与耗时基准，冷缓存和热缓存分开记录。
- README、规划文档和测试账目同步。
- 只提交目标文件，不执行远程操作。

## 12. 验证与验收

### 12.1 Rust 与 Node

必须覆盖：

- 预算等于、超过和溢出边界，结构开销与共享对象只计一次。
- 小操作多步、大操作少步、最旧淘汰、redo 释放和预算调小。
- 固定点取消、失败、成功及后续操作不能越界。
- 内容、行列、排序、表头模式交错撤销和重做。
- 普通保存后的完整身份往返，删除列物化保存与排序保存的取消、确认两分支。
- 大粘贴扩列一次撤销，取消时列和内容零写入。
- 范围命令不产生前端全量任务数组，IPC 块不超过 1 MiB。
- 设置默认值、损坏回退、已打开会话下发和页签独立预算。

### 12.2 内存与操作验收

- 相同 schema 的列历史成本不随文件行数增长。
- 排序历史不保留整行内容或排序键，恒等视图不分配完整排列。
- 可撤销历史账本始终不超过配置预算；执行临时内存单独报告。
- 大复制不向 JavaScript 返回完整 TSV，大粘贴不发送完整二维数组。
- 固定点执行的内存需求不随输入增加完整二维副本；外部 `readText` 的固有完整字符串单独说明。
- 临时文件在关签和正常退出后按所有权清理。

使用合成夹具做自动化测试。手工大文件基准只使用 `E:\simpletable_hdd_test\bench_22gb.csv` 或另行生成的测试副本，不使用、修改或提交真实业务 CSV。

### 12.3 真机与发布

- 所有新行为先亲见预期 RED，再实现 GREEN。
- 前端变更后重新构建 debug/release exe，并核对嵌入时间戳。
- 真机覆盖列撤销、排序和表头历史、固定点、大复制粘贴、保存和清理。
- 最终测试数量按实际结果更新，不沿用本设计中的估算。
- 未运行的检查必须明确报告，不能写成已通过。

## 13. 完成标准

只有同时满足以下条件，整个设计才算完成：

1. 所有指定文档操作都进入统一历史，纯界面状态仍排除。
2. 每文档默认 64 MiB，撤销和 redo 共用，步数由历史体量决定。
3. 普通操作不因文件大而复制整表，大操作不会绕过预算无限占用历史。
4. 单步超限和排序保存按确认建立固定点，后续撤销边界正确。
5. 列执行不再整档物理重写，普通保存不会留下错误身份历史。
6. 大复制粘贴不再产生可避免的全文、二维数组和整包 IPC 副本。
7. 取消与失败保持原状态，临时文件生命周期明确。
8. 全部自动化、真机和内存验收完成并同步文档。
